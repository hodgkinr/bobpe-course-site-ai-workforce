Give Safe Context and Make the Result Usable

Learning objectives: Turn a workplace need into a clear request with goal, audience, context, constraints, and a useful output format; then improve the request through iteration.; Choose what information is appropriate to share, account for privacy, fairness, accessibility, and policy, and retain human accountability.; Select relevant, approved context while protecting unnecessary or sensitive information.; Specify an output format that makes review and next steps practical.

Content

Lecture 2 summary: Give safe context and make the result usable

This lecture emphasizes context selection and output design. Learners separate necessary context from unnecessary or sensitive detail, use fictionalized or minimized examples, and specify a format that supports review and next steps. The lecture demonstrates how a table, checklist, or short draft can serve different needs, and explains that formatting requests do not confer authority or guarantee accuracy. Learners leave with a brief-and-review cycle they can use in the Week 2 activity.

Objectives: provide-safe-context, specify-output-format Estimated viewing time: 10 minutes (script is approximately 1,280 spoken words at 125 words per minute)

Lecture script

Lecture 2 video script: Give safe context and make the result usable

Estimated speaking time: about 10 minutes at 125 words per minute. Objectives: provide-safe-context, specify-output-format.

[OPENING]

A request can be clear and still contain the wrong information. Imagine asking for a summary of a customer complaint by pasting the customer's full name, phone number, order number, and message into a public AI service. The prompt may explain the task perfectly, but it shares details that are not needed for the summary.

Today we will look at two decisions that belong in every task brief: which context is safe and useful to provide, and what output shape will make the response easier to use and review.

[SECTION 1: CONTEXT HAS A JOB]

Context should help the system complete the task. It may include the source material, audience, purpose, or facts that constrain the response. Before you add a detail, ask: “Would the response change in a useful way if I left this out?” If not, leave it out.

Consider the complaint example. The task might be to categorize a fictional message as “delivery,” “billing,” or “product question” and summarize the issue in one sentence. To practice, replace the real message with a made-up one: “A customer says a fictional package arrived two days later than expected and asks where to find the delivery estimate.” The name and phone number do not matter to this classification. The package number does not matter either. A fictional example lets you learn the process without exposing real customer information.

If a real workplace task requires sensitive information, pause and follow the organization's approved tools and procedures. A generic conversational service should not receive personal, employer-confidential, client, student, or regulated information unless the organization has explicitly approved that use and its safeguards. Never assume that a feature label or privacy setting makes a use permitted.

[SECTION 2: MINIMIZE AND TRANSFORM]

You can often make a task safer by minimizing or transforming the input. Remove names, contact details, account numbers, and other identifiers. Replace them with neutral labels such as “Customer A” only when the remaining content is still appropriate to share. Sometimes a fictionalized scenario is safer and just as useful. Sometimes the correct choice is to avoid AI entirely.

Minimizing information is not a guarantee of anonymity. A combination of details can still identify a person, especially in a small group or unusual situation. Do not paste a sensitive record and rely on the model to remove the details afterward. Make the decision before the information enters the service. When in doubt, use an approved channel or consult the relevant policy owner.

[SECTION 3: CHOOSE A FORMAT FOR THE JOB]

Output format should support the next step. If you are comparing options, request a table with columns that reveal the relevant differences. If you need an action sequence, request a numbered checklist. If you need a message, request a short draft followed by a separate list of assumptions to verify. If you need to inspect a transformation, ask for a two-column table showing the source wording and proposed wording.

For example, for fictional event feedback, you might ask: “Group these six made-up comments into up to three themes. Return a table with theme, supporting comment IDs, and a note about any comment that does not fit. Do not infer what all visitors think.” This format keeps the evidence visible. It also makes it easier to detect when the system has stretched one example into a broad claim.

But a format can also hide problems. A tidy table may make uncertain conclusions look official. A confidence score does not prove accuracy. A polished report does not become a policy decision because it has headings. Make sure the output shape helps you inspect evidence rather than giving a draft false authority.

[SECTION 4: INCLUDE A REVIEW PLAN]

A useful brief can say how you will review the response. For a summary, compare it with the source. For a list of facts, check each against an approved document. For a rewrite, confirm that required meaning and details remain unchanged. For a set of ideas, review them for relevance, fairness, and tone.

You can ask the AI to flag uncertain points or list which source details it used, but the response is still a generated aid. If a source list or explanation matters, inspect the sources yourself. Do not treat a model's claim that it “checked” something as proof that a check happened.

The review plan is yours to define. A model may miss its own omission. For example, it might provide a five-item checklist after you asked for seven required steps. Compare the output against the original task and count. A quick human review can catch what the generated response does not mention.

[SECTION 5: ITERATE WITH PURPOSE]

If the first response is weak, diagnose the gap before sending another instruction. Was the goal ambiguous? Was the audience missing? Did you omit a needed fact? Was the requested format unsuitable? Did the output ignore a constraint? A targeted follow-up is usually more useful than “try again.”

For example: “The draft added a registration requirement that was not in the facts. Revise it using only the three details in the prompt, and put any question you cannot answer in a separate note.” The follow-up points to the error, states a boundary, and describes what to do with uncertainty. Then check the revision against the same facts. Iteration improves direction; it does not remove the need to review.

A related question is whether the requested format will make the answer easier for another person to inspect. Imagine that a fictional team needs to shorten a public checklist. A two-column table with “source step” and “shortened step” lets a reviewer compare each item. A five-bullet summary may look cleaner, but it can hide which source steps were combined or omitted. Choosing the format is part of the task design: make the important comparison visible to the person who owns the result.

A helpful brief also says what to do when the context does not contain an answer. For example: “If the event start time is not in the source facts, list it as unknown in a separate note. Do not guess.” That instruction creates a useful place for uncertainty. Still, you need to inspect the response to see whether it followed the instruction. The prompt can invite the model to flag gaps, but the person must decide whether the output actually accounts for them.

Think of the workflow as three distinct moments. First, before sharing, decide whether the input is relevant and appropriate. Second, while framing, state the task, audience, constraints, and useful output shape. Third, before using, compare the result with the evidence and decide what happens next. If you notice an error in the last moment, you can return to the framing step with a focused correction, or stop if the task cannot be made safe or checkable.

This sequence transfers across tools and roles. An interface may change, but the core decisions remain: what information is safe, what task you need done, how the response should be shaped, and how you will check it.

[RECAP AND TRANSITION]

Safe context is relevant, minimized, and appropriate for the service. A fictional or transformed example is often enough for practice. A usable output format should make the next step and review easier, not make the response appear more authoritative. A well-framed request is followed by a human check.

In the activity, you will compare a vague request with a clearer task brief, create a fictional version of the input, and specify the output shape and review criteria. You will have an artifact you can reuse when you begin designing a bounded workflow later in the course.
